Frequently Asked Questions

Authorization API​

What exactly does the Authorize API do?​

The Authorize API (POST /services/{user_id}/auth) does two things in one step:

  1. Checks whether the account has sufficient balance or quota for the requested service units
  2. Locks (reserves) those units in PortaBilling for the duration of the lock_period

Both happen atomically — if the account has enough balance, the units are locked immediately. If not, the request is rejected and nothing is locked.

Under the hood: The gateway sends a RADIUS Access-Request with PortaBilling_Session:lock and PortaBilling_Authorize:base=quantity;max=<units>;max_expires=<lock_period>. PortaBilling validates the account, checks the balance against the requested quantity, and locks the units if the check passes.

Does authorization create an xDR? Is it kept open?​

No. Authorization does not create an xDR. Instead, it creates a session lock — an internal quota reservation (QuotaConstraint) in PortaBilling that holds the requested units against the account's balance for the duration of the lock_period. No billing record exists at this point.

The xDR is only created when a charge request (Accounting-Stop) arrives. At that point, PortaBilling rates the actual consumed units, creates the xDR, and simultaneously releases the session lock.

The lifecycle is:

EventWhat happens in PortaBilling
/auth succeedsSession lock created, funds reserved — no xDR
/charges submittedNew xDR created with actual consumed units; session lock released
/unlock submittedSession lock released with zero units; funds returned to account
lock_period expiresSession lock released automatically — no xDR

The locked_units and expires_at fields in the authorization response describe the current state of this session lock.

What do locked_units and expires_at mean in the auth response?​

  • locked_units — the number of units PortaBilling actually locked (may be equal to or less than the requested units, depending on the account's available quota)
  • expires_at — when the lock will expire if not explicitly released by a charge or unlock request; after this time, PortaBilling automatically releases the lock

Charges API​

What does the Charges API do — does it finalize an existing xDR or create a new one?​

The Charges API always creates a new xDR. Whether or not a prior /auth was called, the Accounting-Stop always creates a fresh xDR with the actual consumed units reported in the request.

The difference when prior authorization was performed is not about xDR finalization — it is about the session lock:

  • With prior auth (same billing_session_id): the session lock is released as part of the same Accounting-Stop, and the xDR is created using the actual consumed units
  • Without prior auth: no session lock exists; the xDR is created directly without any lock to release

In both cases the gateway sends PortaOne-Charge:report=1;commit=complete. The commit=complete flag instructs PortaBilling to only store the xDR if all charges for the event are applied successfully — if any charge component fails, none of them are committed. The report=1 flag tells PortaBilling to return the charge details (amount, quantity) in the RADIUS response, which the gateway then includes in the API response.

What are billing_session_id, session_id, and item?​

FieldWhat it isHow it's used
billing_session_idThe RADIUS h323-conf-id — the primary key that links an authorization session lock to its corresponding chargePortaBilling uses this to identify and release the session lock created during authorization when the charge arrives. Must be the same value in both the /auth and /charges requests for the same session
session_idYour application's internal session identifier (the RADIUS call-id)Used for troubleshooting and reconciliation on your side. Does not affect billing directly
itemThe consumed item / rate code (the RADIUS Called-Station-Id)PortaBilling uses this as the destination to look up the price per unit in the account's tariff

How are billing_session_id and session_id generated?​

session_id: If you don't provide one, the gateway generates a random UUID v1-based identifier. You can provide any unique string that identifies the session on your side.

billing_session_id: The gateway generates it deterministically from your session_id using a UUID v3 (namespace-based hash):

billing_session_id = uuid3(NAMESPACE_DNS, "<session_id>.portaone.com")
  → formatted as "XXXXXXXX XXXXXXXX XXXXXXXX XXXXXXXX" (h323-conf-id format)

This means the same session_id always produces the same billing_session_id — your auth and charge requests for the same session will automatically share the same billing_session_id as long as you use the same session_id in both.

If you provide an explicit billing_session_id in valid h323-conf-id format (XXXXXXXX XXXXXXXX XXXXXXXX XXXXXXXX), it is used as-is. If you provide one in an invalid format, the gateway falls back to generating one from the session_id.

Best practice: Always provide a meaningful session_id. Never rely on random generation for sessions where you need to correlate auth with charge.

Do units represent the charged quantity?​

Yes. units represents the number of billable units of the service. What constitutes one unit depends on your PortaBilling tariff configuration:

ServiceWhat units typically represents
Messaging (SMS)Number of message segments (not messages — a multi-segment message should have units equal to the number of segments)
EV chargingKilowatt-hours (kWh)
AI inferenceNumber of tokens
VoiceSeconds or minutes (depending on tariff configuration)
DataKilobytes or megabytes

Note: charged_units in the response may differ from the requested units due to minimum billing rules or rounding configured in the tariff (e.g., "minimum billed amount is 60 seconds").

How does the system determine the applicable cost per country or network? There are no MCC, MNC, or destination parameters.​

The item field is the destination/routing parameter. PortaBilling uses the item value as a destination pattern to look up the price in the tariff. This is how country- or network-specific pricing works.

Your application is responsible for setting item to a value that matches the correct destination in the tariff:

  • For a country-based SMS tariff, set item to the country dialing prefix (e.g., 44 for the UK, 1 for the US)
  • For a network-based tariff, set item to the operator-specific prefix (e.g., 44ORANGE, 44VODAFONE)
  • For a fixed rate across all destinations, use a single catch-all destination (e.g., SMS)

The PortaBilling administrator configures the destination patterns and rates in the tariff. Your application must know which destination pattern to use based on the subscriber's network or country. If no matching destination is found, PortaBilling returns an unmatched destination error.

For messaging, a single message can be split into multiple segments. How is this handled?​

Set units to the number of segments, not the number of messages. Each segment is billed as one unit.

Example: A 250-character SMS is split into 2 segments:

{
  "service_type": "Quantity",
  "access_code": "SMS",
  "item": "44",
  "units": 2
}

The tariff is configured with a price per segment. PortaBilling multiplies the segment count by the rate to compute the charge.

If your platform bills per message (regardless of segments), set units: 1 and configure the tariff to price per message.

What does perform_authorization do?​

Controls whether the gateway performs a balance/quota check before charging:

ValueBehavior
false (default)Charges immediately without authorization. Suitable when you already performed authorization via /auth, or when you accept the risk of overdraft (the charge proceeds even if the account has insufficient balance)
trueAuthorization is performed first for all service elements. Only if all succeed does the gateway proceed to charge. If any authorization fails, no charges are applied

When to use true: When you want a single-step authorize-then-charge without a separate /auth call, and you need to guarantee no service is delivered unless billing is confirmed in advance.

When to use false: When you already called /auth and have the billing_session_id ready to close, or when your use case accepts post-hoc billing (e.g., low-risk low-value transactions).

Does timestamp represent the billing time?​

Yes. The timestamp field maps to the RADIUS Event-Timestamp attribute and represents when the billable event occurred (not when the API request was made). PortaBilling records this as the time of the xDR.

This is useful when charging is reported with a delay (e.g., a message was sent at 14:00 but the delivery confirmation arrived at 14:05 — set timestamp to 14:00 to record the correct billing time).

If timestamp is not provided, the gateway uses the current time of the API request.

Unlock API​

Does the Unlock operation release the locked funds?​

Yes. The Unlock API (DELETE /services/{user_id}/unlock) sends a RADIUS Accounting-Stop with PortaBilling_Session:unlock and zero consumed units to PortaBilling. This releases the session lock — the reserved balance is returned to the account and becomes available immediately.

Because authorization never created an xDR, there is no billing record to cancel. The account simply has its locked quota freed.

Important: The billing_session_id you provide must match the one returned by the /auth response for the same session. If there is no matching active session lock in PortaBilling (e.g., the lock already expired or was already released by a prior charge/unlock), the request has no effect on the balance.

Balance and xDR Queries​

Do the Charge and Authorize APIs return the remaining balance?​

No. Neither the authorization response nor the charge response includes the account's remaining balance. The API returns:

  • Authorization: locked_units, expires_at, currency
  • Charge: charged_units, charged_amount

The balance is not exposed in the current REST API responses.

To obtain real-time balance: Query PortaBilling's BillingAdmin API or ESPF API directly using the i_user (i_account) value returned in the charge response. The i_user field gives you the PortaBilling internal account identifier, which you can use to query the account's current balance via PortaBilling's native API.

How do I find the xDR created by a charge request? The response does not include an xDR ID.​

The API response does not return a direct xDR ID. To locate the xDR in PortaBilling:

  1. Use the billing_session_id returned in the API response — this is the h323-conf-id that PortaBilling stores with each xDR
  2. In PortaBilling's xDR viewer, search by h323-conf-id using the billing_session_id value
  3. Alternatively, use the i_user (i_account) value from the charge response to look up all xDRs for the account and filter by timestamp

For programmatic xDR lookup, use PortaBilling's ESPF API (/xdr/list or equivalent) with the h323_conf_id filter.

Can I retrieve the details of locked funds?​

Not directly through the Web Charging Gateway API. The authorization response tells you what was locked (locked_units, expires_at), but there is no endpoint to query currently locked sessions after the fact.

If you need to inspect active session locks:

  • Store the billing_session_id and expires_at from the authorization response in your own application state — this is the primary source of truth for what is locked and until when
  • Use PortaBilling's administration interface or ESPF API to query active session locks for an account

Failure Handling​

What happens if xDR creation fails?​

If PortaBilling cannot create the xDR (e.g., tariff configuration error, account issue), it returns an error in the RADIUS Accounting-Response. The gateway translates this to an element in failed_service_elements with error_account and/or error_vendor populated.

The API response will still have HTTP status 200, but success will be false and the service element will appear in failed_service_elements. No charge is recorded in PortaBilling.

Your application must check failed_service_elements on every charge response — a 200 OK does not guarantee all charges succeeded.

Best Practices for Messaging Flows​

How to verify the customer has sufficient balance before sending a message?​

Call POST /services/{user_id}/auth before sending the message:

{
  "service_elements": [{
    "session_id": "<your-message-id>",
    "service_type": "Quantity",
    "access_code": "SMS",
    "item": "<destination-prefix>",
    "units": <segment_count>,
    "lock_period": 120
  }]
}

If the response has a non-empty failed_service_elements, the account cannot cover the charge — do not send the message.

If authorization succeeds, the funds are locked for lock_period seconds. Proceed to send the message within that window.

How to handle "charge on submission" vs "charge on delivery"?​

Charge on submission (charge when the message is sent to the carrier):

Use POST /services/{user_id}/charges with perform_authorization: true. Authorization and charging happen in a single API call. The session lock is created and immediately released as the xDR is written — all in one Authorize→Accounting sequence inside the gateway.

Charge on delivery (charge when confirmed delivered):

  1. On submission: call POST /services/{user_id}/auth to lock funds. Keep the billing_session_id.
  2. On delivery confirmation: call POST /services/{user_id}/charges with perform_authorization: false, passing the same billing_session_id. The session lock is released and a new xDR is created with the actual charge.
  3. If delivery fails: call DELETE /services/{user_id}/unlock with the same billing_session_id. The session lock is released and funds are returned — no xDR is created.

How to release funds if delivery fails?​

Call DELETE /services/{user_id}/unlock with the billing_session_id from the authorization response:

{
  "billing_session_id": "<from auth response>",
  "session_id": "<your-message-id>",
  "service_type": "Quantity",
  "access_code": "SMS",
  "item": "<destination-prefix>"
}

The session lock is immediately released and the funds are returned to the account balance. No xDR is created.

Do this within the lock_period window. After the lock expires, PortaBilling releases the funds automatically — so an explicit unlock after expiry has no effect.

How to adjust the charge based on the confirmed network (when network confirmation arrives after charging)?​

This is a two-step flow. The key constraint is that the item (destination/rate code) must be fixed at the time of charging because it determines the tariff applied. You have two options:

Option A — Charge on confirmation (recommended): Use the authorize-on-submission, charge-on-delivery pattern. At authorization time, use a conservative item (e.g., a generic catch-all destination). At charge time, when you know the actual network, use the confirmed network-specific item:

  1. /auth with item: "SMS" (generic rate) → funds locked
  2. Carrier confirms: message delivered via UK Orange (prefix 44ORANGE)
  3. DELETE /unlock with the authorization billing_session_id (releases the generic lock)
  4. /charges with item: "44ORANGE" (exact network rate), perform_authorization: false

Note: Because /unlock releases the original session lock and /charges creates a new xDR, the final xDR will be associated with a new billing_session_id derived from the same session_id. Use your application's session_id to correlate the authorization and the final charge in your records.

Option B — Charge at submission with correction xDR: Charge at submission using a conservative/average rate. When the actual network is confirmed and differs significantly, submit a correction using a second charge or a credit note through PortaBilling's BillingAdmin API.

Option A is generally preferred as it produces a single accurate xDR per message and avoids correction complexity.

General​

Why does the API return HTTP 200 even when a service element fails?​

The HTTP status code reflects whether the gateway request itself was processed, not whether all billing transactions succeeded. A 200 means the gateway successfully communicated with PortaBilling and received a response.

Individual billing outcomes are reported per element in service_elements, failed_service_elements, and unprocessed_service_elements. Always inspect these arrays — do not rely on the HTTP status code alone to determine whether a charge was applied.

Why might charged_units differ from the units I sent?​

PortaBilling may apply minimum billing rules or rounding configured in the tariff. For example:

  • A tariff with "minimum billed duration: 60 seconds" will charge 60 seconds even if only 10 seconds were consumed
  • A tariff that rounds up to the nearest whole unit will round 1.3 units to 2

charged_units in the response always reflects what PortaBilling actually billed. charged_amount reflects the cost of charged_units at the configured rate.

Is there a timeout on locked funds?​

Yes — the lock_period parameter (in seconds) you set in the authorization request determines how long PortaBilling holds the lock. Default is 300 seconds (5 minutes).

After the lock expires, PortaBilling automatically releases the session lock and the funds become available again. There is no xDR created by the expiry itself. A subsequent charge request using the same billing_session_id after expiry will still create an xDR successfully — it will simply be processed without the benefit of the pre-authorized lock (the quota will be checked at charge time instead).

Always ensure your charge or unlock request arrives within the lock_period window. Set lock_period conservatively for your workflow — long enough to accommodate network delays and retries, but short enough not to hold funds unnecessarily.
