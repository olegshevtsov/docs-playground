Authentication

All service endpoints on the Web Charging Gateway require a valid Bearer token. This document explains how to obtain tokens, use them, and choose the right authentication method for your deployment.

Two Authentication Methods​

LocallyConfiguredUser​

A single static username and password are configured in the portal. The gateway issues and validates JWTs using secrets that are automatically managed by the Add-on Mart platform.

When to use: Simple or single-tenant deployments where you want to manage API credentials directly in the portal, without connecting to PortaBilling's admin interface.

Portal configuration:

  • Set Method of authentication to LocallyConfiguredUser
  • Fill in Locally configured user login and Locally configured user password

BillingAdmin​

The gateway delegates login to PortaBilling's BillingAdmin API (/Session/login). When a client logs in, their credentials are forwarded to BillingAdmin, which validates them and manages token issuance.

When to use: Environments that require centralized credential management within PortaBilling's user management interface. Ideal for tighter security control where API users are managed as PortaBilling administrator or staff accounts.

Portal configuration:

  • Set Method of authentication to BillingAdmin

PortaBilling user requirements:

  • The user must exist as an administrator or staff account in PortaBilling
  • Required API scopes: espf.api:write espf.handlers:write

Important: Two Independent Security Layers​

The gateway uses two separate security mechanisms that operate independently:

LayerWhat it protectsHow it works
JWT authenticationAccess to the REST APIClient logs in and presents Bearer token with each request
RADIUS trustBilling/charging traffic to PortaBillingGateway identifies itself by NAS IP + RADIUS shared secret

Your application's login credentials (and JWT tokens) have no effect on the RADIUS communication layer. Even if a token is compromised, an attacker cannot directly communicate with PortaBilling — they can only call the gateway's REST API.

Token Flow​

1. Login​

Send credentials using application/x-www-form-urlencoded (OAuth2 password flow):

curl -X POST https://<your-portal-domain>/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=your-api-username&password=your-api-password"

Response:

{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_at": "2024-06-01T12:00:00"
}
FieldDescription
access_tokenJWT for authenticating service requests. Include in Authorization: Bearer header
refresh_tokenLong-lived token for obtaining a new access token without re-entering credentials
expires_atWhen the access token expires (ISO 8601 datetime)

Default token lifetimes (configurable in the portal):

  • Access token: 2 days (172800 seconds)
  • Refresh token: 30 days (2592000 seconds)

2. Use the Access Token​

Include the access token in the Authorization header of every service request:

curl -X POST https://<your-portal-domain>/services/john.doe@example.com/charges \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." \
  -H "Content-Type: application/json" \
  -d '{ ... }'

If the token is missing or invalid, the gateway returns 401 Unauthorized.

3. Refresh the Access Token​

Before the access token expires, use the refresh token to obtain a new one without re-entering credentials:

curl -X POST https://<your-portal-domain>/refresh-token \
  -H "Content-Type: application/json" \
  -d '{
    "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
  }'

Response:

{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_at": "2024-06-03T12:00:00"
}

If the refresh token has also expired, the client must log in again with credentials.

Best Practices​

  • Store tokens securely — never log or persist access tokens in plaintext
  • Implement proactive token refresh: check expires_at and refresh before expiry rather than waiting for a 401
  • Use short-lived access tokens in combination with refresh tokens for a good balance between security and user experience
