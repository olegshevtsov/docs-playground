Security Guide

The Web Charging Gateway has two independent security layers. Understanding both is important for a secure production deployment.

Layer 1: REST API Authentication (JWT)​

Controls who can call the gateway's REST API.

JWT Secrets​

When using the LocallyConfiguredUser authentication method, the gateway signs JWTs with two secrets. These secrets are automatically generated and managed by the Add-on Mart platform — you do not configure them directly.

Token Handling Best Practices​

  • Store tokens securely in your application (never in localStorage for browser apps; use httpOnly cookies or server-side session storage)
  • Do not log access or refresh tokens
  • Implement proactive token refresh before expiry to avoid service interruptions
  • Token lifetimes are configured in the portal (Access token expiration time and Refresh token expiration time)

BillingAdmin Authentication​

When using BillingAdmin mode, credentials are validated by PortaBilling. Follow PortaBilling's user management security practices for managing admin/staff accounts.

Layer 2: RADIUS Communication Security​

Controls the trust between the gateway and PortaBilling's RADIUS server.

NAS IP Trust​

PortaBilling only accepts RADIUS packets from IP addresses registered as trusted Nodes. If the source IP of a RADIUS packet does not match a configured Node's NAS IP, PortaBilling silently discards the packet.

  • The NAS IP in the portal must exactly match the NAS IP configured on the Node in PortaBilling
  • Mismatches cause all RADIUS requests to fail silently (no error response, just timeout)

RADIUS Shared Secret​

The PortaBilling secret in the portal authenticates and encrypts RADIUS packets between the gateway and PortaBilling.

  • Use a strong secret: mix of uppercase letters, lowercase letters, and numbers
  • Maximum length: 32 characters
  • Must exactly match the secret configured on the Node entry in PortaBilling

Network-Level Security​

RADIUS communication uses UDP on ports 1812 (auth) and 1813 (acct). There is no TLS or DTLS support — the RADIUS protocol relies on the shared secret for message authentication.

Requirements:

  • The gateway and PortaBilling RADIUS server should be on the same private network or connected via a secure VPN
  • Do not expose RADIUS ports to the public internet
  • Firewall rules should permit UDP 1812/1813 only from the gateway's NAS IP to the RADIUS server

CORS Configuration​

CORS controls which browser origins can call the REST API. This matters when your web application makes calls directly from the browser.

Configure CORS in the portal under CORS configuration:

  • Development: The default * in CORS allow origins allows any origin. This is acceptable during development.
  • Production: Replace * with your application's explicit domain (e.g., https://yourapp.example.com). Clear the wildcard to prevent unauthorized browser-based clients from calling your API.
  • Do not enable CORS allow credentials when using wildcard origins.
